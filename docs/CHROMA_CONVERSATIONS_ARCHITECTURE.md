# Архитектурный план: Хранение переписок в ChromaDB

## 1. Обзор

### 1.1 Цель
Интеграция векторной базы данных ChromaDB для хранения и семантического поиска по истории переписок (messages) между агентами и LLM в мультиагентной системе поиска работы.

### 1.2 Текущее состояние
- **Хранение переписок**: В памяти во время выполнения (`AgentState.messages`), после завершения - частично в JSON файлах сессий
- **ChromaDB**: Уже интегрирована через MCP для вакансий, сопроводительных писем и резюме
- **Расположение БД**: `/Users/alxy/Desktop/1PROJ/PrometheusAi/job_searcher_agent/chroma_data`

### 1.3 Преимущества
- **Семантический поиск** по истории переписок для поиска похожих ситуаций
- **Контекстное извлечение** релевантных диалогов для улучшения работы агентов
- **Анализ паттернов** успешных взаимодействий
- **Масштабируемость** - векторный поиск эффективнее полного сканирования JSON файлов

## 2. Архитектура данных

### 2.1 Структура переписок

**Типы сообщений (LangChain BaseMessage):**
- `SystemMessage` - системные инструкции и промпты
- `AIMessage` - ответы LLM, включая tool_calls
- `ToolMessage` - результаты выполнения инструментов
- `HumanMessage` - пользовательские запросы (если есть)

**Структура для хранения в ChromaDB:**
```python
{
    "document": "Текст переписки (конкатенация всех сообщений)",
    "metadata": {
        "session_id": str,
        "agent_name": str,  # "planner", "browser_agent", "cover_letter_agent"
        "timestamp": str,  # ISO format
        "message_count": int,
        "vacancy_url": str | None,  # Если переписка связана с вакансией
        "vacancy_title": str | None,
        "action_type": str,  # "planning", "browsing", "cover_letter_generation", "error_handling"
        "successful": bool,  # Успешно ли завершилась операция
        "error_type": str | None,  # Тип ошибки если была
        "tools_used": str,  # Список использованных инструментов через запятую
        "message_types": str,  # "SystemMessage, AIMessage, ToolMessage"
    },
    "id": str  # Уникальный ID переписки
}
```

### 2.2 Коллекция в ChromaDB

**Имя коллекции:** `conversations` или `agent_conversations`

**Описание:** Коллекция для хранения переписок между агентами и LLM с возможностью семантического поиска по контексту диалогов.

## 3. Компоненты системы

### 3.1 Модуль `mas/chroma_utils.py` - Расширение

**Новые функции:**

1. **`ensure_conversations_collection(chroma_tools: dict) -> bool`**
   - Проверяет существование коллекции `conversations`
   - Создает коллекцию если не существует
   - Возвращает статус готовности

2. **`store_conversation(chroma_tools: dict, messages: List[BaseMessage], session_id: str, agent_name: str, metadata: dict) -> bool`**
   - Конвертирует список BaseMessage в текстовый формат
   - Извлекает метаданные (использованные инструменты, типы сообщений)
   - Сохраняет в ChromaDB с нормализацией метаданных
   - Генерирует уникальный ID переписки

3. **`search_similar_conversations(chroma_tools: dict, query_text: str, agent_name: str | None, n_results: int = 5) -> List[Dict]`**
   - Семантический поиск похожих переписок
   - Опциональная фильтрация по агенту
   - Возвращает релевантные переписки с метаданными

4. **`get_conversation_context(chroma_tools: dict, session_id: str, agent_name: str | None) -> str`**
   - Получает контекст переписок для текущей или предыдущих сессий
   - Форматирует для использования в промптах
   - Ограничивает количество результатов для экономии токенов

5. **`format_messages_for_storage(messages: List[BaseMessage]) -> str`**
   - Конвертирует BaseMessage в читаемый текстовый формат
   - Сохраняет структуру диалога (System/AI/Tool)
   - Обрезает длинные результаты инструментов

### 3.2 Интеграция в узлы графа

#### 3.2.1 Supervisor Node
- **Действие**: Сохраняет ключевые переписки при переходе между агентами
- **Когда**: После завершения работы каждого агента
- **Что сохранять**: Последние N сообщений перед переходом

#### 3.2.2 Planner Node
- **Действие**: 
  - Загружает контекст похожих планирований из прошлого
  - Сохраняет переписку после создания плана
- **Когда**: 
  - В начале работы - загрузка контекста
  - После генерации плана - сохранение

#### 3.2.3 Browser Agent Node
- **Действие**:
  - Загружает контекст успешных/неуспешных взаимодействий с браузером
  - Сохраняет переписки при критических операциях (логин, поиск, отклик)
- **Когда**:
  - При ошибках - для анализа паттернов
  - После успешных операций - для обучения

#### 3.2.4 Cover Letter Agent Node
- **Действие**:
  - Загружает примеры успешных генераций писем
  - Сохраняет переписку генерации письма
- **Когда**:
  - Перед генерацией - загрузка примеров
  - После генерации - сохранение

## 4. Стратегия хранения

### 4.1 Что сохранять

**Обязательно:**
- Переписки с ошибками (для анализа паттернов проблем)
- Переписки успешных операций (логин, отклик, генерация письма)
- Переписки планирования (для улучшения планов)

**Опционально:**
- Промежуточные переписки (можно фильтровать по длине или важности)
- Переписки с tool_calls (для анализа использования инструментов)

### 4.2 Когда сохранять

**Вариант 1: Пакетное сохранение (рекомендуется)**
- Сохранять переписки в конце работы каждого агента
- Сохранять все переписки сессии при завершении
- **Плюсы**: Меньше нагрузка на ChromaDB, меньше дубликатов
- **Минусы**: Риск потери данных при сбое

**Вариант 2: Инкрементальное сохранение**
- Сохранять после каждого значимого действия
- **Плюсы**: Меньше риск потери данных
- **Минусы**: Больше нагрузка, возможны дубликаты

**Рекомендация**: Использовать **Вариант 1** с опциональным инкрементальным сохранением для критических операций.

### 4.3 Ограничения и оптимизация

**Ограничения:**
- Максимальная длина документа в ChromaDB (обычно ~100K символов)
- Количество метаданных (ChromaDB имеет ограничения)
- Производительность при большом количестве записей

**Оптимизация:**
- Обрезать длинные результаты инструментов (MAX_TOOL_RESULT_SIZE)
- Группировать короткие переписки в один документ
- Использовать фильтры при поиске для уменьшения объема данных
- Периодическая очистка старых переписок (опционально)

## 9. Производительность и масштабируемость

### 9.1 Оценка объема данных

**На одну сессию:**
- Средняя переписка агента: ~10-50 сообщений
- Размер текста: ~5-20 KB на переписку
- Метаданные: ~1-2 KB

**При 100 сессиях:**
- ~300-500 переписок (по 3-5 на сессию)
- Общий объем: ~1.5-10 MB текста + метаданные

**Вывод**: ChromaDB легко справится с таким объемом данных.

### 9.2 Оптимизация поиска

- Использовать фильтры по `agent_name`, `session_id`, `successful`
- Ограничивать `n_results` разумными значениями (3-10)
- Кэшировать частые запросы (опционально)

### 9.3 Очистка данных

**Стратегии:**
- Хранить только последние N сессий (например, 100)
- Периодическая архивация старых переписок
- Удаление переписок неуспешных сессий старше X дней (опционально)

## 10. Безопасность и приватность

### 10.1 Чувствительные данные

**Что может содержаться в переписках:**
- Логины/пароли (в tool results) - **НЕ сохранять**
- Персональные данные из резюме
- URL вакансий и компаний

**Меры:**
- Фильтровать чувствительные данные перед сохранением
- Не сохранять переписки с tool_calls, содержащими пароли
- Очищать результаты инструментов от персональных данных

### 10.2 Доступ к данным

- ChromaDB данные хранятся локально
- Нет сетевого доступа (persistent mode)
- Рекомендуется добавить опцию шифрования (опционально)

## 12. Альтернативные подходы

### 12.1 Хранение в JSON + векторный поиск

**Подход**: Хранить переписки в JSON, но индексировать только ключевые части в ChromaDB.

**Плюсы**: Полная история в JSON, быстрый поиск в ChromaDB
**Минусы**: Дублирование данных, сложнее синхронизация

### 12.2 Отдельная коллекция для каждого агента

**Подход**: `conversations_planner`, `conversations_browser`, etc.

**Плюсы**: Лучшая изоляция, проще фильтрация
**Минусы**: Больше коллекций, сложнее управление

**Рекомендация**: Использовать одну коллекцию с фильтрацией по `agent_name`.
